# Security: What a Widget Reads

The files a preview reads and the checkout a diff reads: in both, tmux decides what may be read, and what is read is untrusted. Part of [SECURITY.md](SECURITY.md), beside [SECURITY-CONTENT.md](SECURITY-CONTENT.md).

## A Preview Reads One File

`tmuxy open <file>` shows a local markdown document or HTML page in a pane (the `preview` widget, see [ARCHITECTURE-WIDGETS.md](ARCHITECTURE-WIDGETS.md)). A file is the least trusted thing tmuxy draws: a page downloaded from anywhere, a README from a cloned repository, a report a tool wrote from data it did not check. The design assumes the document is hostile and keeps two questions apart — what it may **read**, and what it may **do**.

**What may be read is decided by tmux, not by the client or the document.** The UI reads the file through a client command, `read_preview`, naming only the pane; the path is the pane's `@tmuxy-pane-preview`, honoured only while `@tmuxy-pane-widget` is `preview`. `tmuxy-widget-preview` writes both out of band through `run-shell` and the widget clears its tag on exit, so neither pane output nor a client can point a preview at another file, and a pane that has gone back to being a shell reads nothing. Both transports call the same check (`tmuxy_core::preview`), on every read; nothing serves an arbitrary path.

**A document's own references are held to its folder.** A resource the document links — a stylesheet, a script, an image, a font — is read only when its path, relative to the document, stays inside the document's folder once symlinks are resolved, passes through no hidden name (`.ssh`, `.env`, `.git`, `..`), and is a type a page loads (`FILE_TYPES` in `tmuxy-core/src/mime.rs`). A hostile page in `~/Downloads` cannot name `../.aws/credentials` as a stylesheet, nor `notes.txt` beside it. Every read is a regular file (checked before the open and on the descriptor, no symlink followed) under a size cap (`MAX_DOCUMENT_BYTES` 8 MiB a document, `MAX_RESOURCE_BYTES` 16 MiB a resource; a composed page a client stages for a pane's frame, `MAX_STAGED_BYTES`, 48 MiB — `tmuxy-core/src/preview.rs`), done off the async workers. The client applies the same rules before it asks (`domain/preview.ts`) so that what the server would refuse costs no round trip, but the server's check is the one that holds.

**What a document may do depends on what it is.**

- **Markdown is rendered by the app**, in the app's own origin, so nothing in it may execute: raw HTML in the document is not rendered at all, a link opens in the system browser only when it is `http(s)` or `mailto` and never navigates the app, and a remote image is not loaded unless the preview was opened with `--net`, since loading it tells its host the document was read — and then without a referrer. A ```mermaid or ```pele fence becomes an SVG on this side of the boundary, where anything that executes can drive the API.
  - **Pele draws the diagram from its text alone**, with no document to lay it out in, its links held to `http(s)` and its pictures refused without `--net` (`components/widgets/preview/DiagramBlock.tsx`). What pele cannot draw goes to mermaid, which lays a diagram out by drawing it into a live document. So mermaid runs in sandbox mode, in a frame of the app's origin that `drawMermaid.ts` sandboxes before the frame's document exists (`allow-same-origin` only: mermaid can reach in to measure, nothing in it can run), with a policy that fetches nothing but `data:` pictures (and the web's with `--net`). Mermaid's own sandbox frame is not enough: it gets its `sandbox` attribute only after insertion. A `$$…$$` formula is drawn as its text by both.
  - **What comes back is sanitized at the sink** (`components/widgets/preview/sanitizeSvg.ts`), by allowlist: parsed in an inert document; out of a label only the SVG elements a diagram is drawn with, in a label only HTML text formatting, and `<title>`/`<desc>` as their text alone (the HTML parser builds HTML inside them, as it does in a label); every `on*` attribute and every attribute that sends a request or opens a window (`ping`, `rel`, `target`, …) removed; `<style>` held to rules scoped to the id the block drew the diagram under, never one the markup claims; nothing in CSS or an attribute that fetches (`url(` other than a same-document `url(#…)`, `src(`, `image(`); a link's `href` narrowed to `http(s):` and same-document fragments, an `<image>`'s to `data:image/` (plus `http(s):` with `--net`), anything else to fragments.
  - **The block clips what it draws** (`contain: paint`), so no markup in a diagram can lay itself over the app. A link click, left or middle, opens the system browser and never navigates the app. Mermaid's theme options are locked (`secure`), so a diagram's `%%{init}%%` cannot bring CSS of its own. Two layers: mermaid has had bypasses before, and the blast radius here is a shell.
- **A page runs in a sandboxed frame**, served under a policy of its own (`page_csp`): `sandbox allow-scripts` without `allow-same-origin`, so the page has an opaque origin — no cookies, no storage, no access to the app's DOM or API; it cannot open windows, submit forms, or navigate the app — and, unless the preview was opened with `--net`, nothing may be fetched at all (`connect-src 'none'`, images and fonts from `data:` only). The resources beside it are inlined into the page by the client, through `read_preview` under the rules above, before it is staged; `<base>` and `<meta http-equiv>` are taken out, so the page can neither re-aim its references nor add a policy that overrules the served one. The page reaches tmuxy's API no more than any other site does: its requests come from an opaque origin, which the [request guard](SECURITY-NETWORK.md#cross-origin-requests) refuses.

  The policy is a response header rather than a `srcdoc`, because a `srcdoc` frame inherits the embedding app's policy — the desktop app forbids inline script, which would stop the page and the bridge alike — and because a meta tag is the document's to precede. So the client stages the composed page (`POST /api/preview/{pane}` on the web, `stage_preview` on the desktop), the server checks with tmux that the pane is previewing a page and takes `--net` from tmux too, never from the client, and the frame loads it from `GET /api/preview/{pane}` or the `tmuxypreview:` scheme with the policy as a header. Both routes exist only on a writable server.

**The page talks to the app through one narrow bridge** (`components/widgets/preview/previewBridge.ts`): a script put first in the page posts where it is scrolled to (so a reload after the file changes opens in the same place), its `<title>`, a link the user followed (opened in the system browser when it is `http(s)` and leaves tmuxy), and a Ctrl or Alt chord pressed in the page — without which Ctrl+C would never reach the widget and the prefix never reach the app. Anything can post a message, so the app accepts one only from its own frame, in one of those four shapes, signed with a token made per composition, which the bridge takes before the page's scripts run; it forwards only user-made keys and clicks, to the app's origin alone (a `--net` page framing its own URL would read the token otherwise). The app replays a chord only while that frame holds the keyboard; it then moves the keyboard to the pane, so a page cannot follow one replayed chord with another, and a plain key is never replayed at all. A replayed chord reaches only Ctrl+C, the prefix and root bindings that move between panes or tabs (`keyboardActor.ts`). Ctrl/Cmd+Enter is never replayed either, and the app answers waiting `pane send` questions with it only from a trusted (user-made) key event. An inlined stylesheet cannot close its `<style>` (`</style` is escaped as CSS), so a local `.css` file cannot add markup after the page's `<base>`, `<meta http-equiv>` and `<noscript>` were removed.

**What a preview does not protect.** A document opened with `--net` can tell a remote host anything it can read — which, by the rules above, is its own folder's pages, styles, scripts and pictures. A page's scripts run, in an opaque origin, which is what local reports and charts need. And a preview shows the user what the file says: a convincing fake prompt drawn by a page is a page, in a pane whose header names the file.

## A Diff Reads One Checkout

`tmuxy widget diff [folder]` shows a git checkout's changes in a pane (the `diff` widget). The checkout is anyone's: a clone, a pull request checked out, a branch an agent wrote. Its config can name programs for git to run, and its file names and lines are text someone else chose.

**What may be read is decided by tmux, not by the client.** The UI reads through `read_diff`, naming only the pane and a scope (unstaged, staged, or the branch against its base). The checkout is the pane's `@tmuxy-pane-diff`, honoured only while `@tmuxy-pane-widget` is `diff`; `tmuxy-widget-diff` writes both out of band through `run-shell`, after checking the pane is its caller's own, and the widget clears its tag on exit, so the read is refused from then on.

**git runs nothing the repository names** (`tmuxy-core/src/diff_review/git.rs`). No filesystem monitor, hook, pager, credential helper or transport; no external diff and no textconv; every content filter driver the config holds switched off, so a filtered file is compared as the text it is; no submodule; the variables that would point git elsewhere or add config scrubbed. The plumbing commands read the index as it is and never write it, so the user's own commit is never held up by a lock. Each read has a deadline and a cap on what it returns. A test sets a trap for each of these and checks none fires.

**What git prints is drawn as text.** File names and lines are strings in the answer, put on screen as text nodes only: a line of markup is shown as written. The read returns the checkout's folder name, never its path.

## A Review Types Into One Agent, Never At A Question

A diff's comments go to an agent as one numbered prompt (`domain/review.ts`, `components/widgets/diff/ReviewBar.tsx`): pasted into the pane the review bar names, then Enter. Only a pane of the widget's own tab running an agent (`agent_screen::AGENT_COMMANDS`, generated into the UI) is offered; `tmuxy widget diff --to %N` only preselects one, and the script takes nothing but a pane id there.

| Risk | What holds it |
| ---- | ------------- |
| The prompt answers a permission question | Two checks. The client's `sendRefusal` refuses while the pane reads `needs-input`. Then tmux checks again as it sends: the paste and the Enter run inside one `if-shell -F` on `agent_takes_input_format` (`commandHelpers.ts` `reviewInto`), so a dialog raised after the client looked gets no keys; the staged review is dropped, a message says so, and Restore brings the comments back. Both give way to `pane send`'s own refusal once that exists |
| The prompt reaches a shell | A shell would run each line, and a quoted `   > code` line is a redirection that empties a file. No pane but an agent is offered, and the same `if-shell` requires an agent's process, so an agent that exited in the meantime leaves a shell that gets nothing |
| The review's text drives the program | It goes as a paste: control characters dropped, bracketed when the program asked for it, to that pane alone even in a synchronized window |
| The checkout's text runs as markup in the widget | A comment and the line it quotes are text nodes, as every diff line is |

An agent tmuxy installs no hooks for (Gemini CLI, Aider) is never offered: nothing would say when it waits for an answer. What tmux can see is the limit: a dialog no hook has declared and the screen pass has not read yet (it reads every 1.5 s) still looks like an agent at work. Held by `tests/14-widget-diff.test.js` (a fake agent reads the prompt; then the send is held after the client's check while the agent raises a question, and nothing reaches it; then its shell is offered nothing), `tests/agent_takes_input.rs` (the format, asked of a real tmux) and `domain/__tests__/review.test.ts`.
